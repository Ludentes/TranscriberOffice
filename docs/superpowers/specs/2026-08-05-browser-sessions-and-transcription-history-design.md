# Browser Sessions and Transcription History

## Goal

Allow an anonymous user to start a transcription, reload or close the tab, and
later return from the same browser to see the task and its result. A user must
never be able to list, open, stop, delete, or download another browser's tasks.

The feature also adds a persistent history of completed transcriptions. Results
can be copied in the UI or downloaded as UTF-8 text and JSON.

## Scope

This design includes:

- anonymous browser identity stored in a protected cookie;
- persistent jobs, progress, and results;
- a background worker independent of a Gradio request;
- recovery after a page reload and an application restart;
- per-browser history and task details;
- TXT and JSON downloads;
- task cancellation and history deletion;
- automatic removal of source audio after a terminal task state.

This design does not include accounts, passwords, cross-browser history,
sharing, administrator access, or resuming model generation from the exact
token/chunk where a process stopped.

## User Identity and Security Boundary

FastAPI middleware ensures that every browser has a random 256-bit opaque token
in a cookie. The cookie is configured with `HttpOnly`, `SameSite=Lax`, a long
expiration, and `Secure` when HTTPS is enabled. The server stores only a
SHA-256 hash of the token and associates it with an internal owner ID.

The cookie is a bearer credential: a person who obtains it can access that
browser's history. It therefore must not be logged or returned in API bodies.
Clearing the cookie permanently disconnects the browser from its prior history;
there is no recovery mechanism without user accounts.

Every read or mutation uses both `job_id` and the resolved `owner_id`. Looking
up a foreign job returns `404`, rather than revealing that it exists. File paths
are generated by the server and are never accepted from the client.

## Persistent Data Model

SQLite is used because the application currently runs as one service with one
GPU worker and needs no external database. Connections use WAL mode, foreign
keys, a busy timeout, and short transactions.

### owners

- `id`: internal UUID, primary key;
- `token_hash`: unique SHA-256 digest;
- `created_at`;
- `last_seen_at`.

### transcription_jobs

- `id`: public random UUID, primary key;
- `owner_id`: required foreign key;
- `original_filename`: display/download metadata only;
- `audio_path`: server-generated private path, nullable after cleanup;
- `hotwords`;
- `status`: `queued`, `running`, `completed`, `failed`, or `canceled`;
- `progress_text`: latest safe status or partial transcript;
- `result_text`: final formatted transcript;
- `result_json`: final structured result;
- `error_message`: sanitized user-facing failure;
- `cancel_requested`: boolean;
- `created_at`, `started_at`, `completed_at`, `updated_at`;
- `attempt_count`.

Indexes cover `(owner_id, created_at)` and `(status, created_at)`.

## Storage Layout

Application data lives under a configurable data directory, defaulting to
`./data`:

- `data/transcriber.sqlite3` contains owners, jobs, and results;
- `data/uploads/<job-id><validated-extension>` temporarily contains source
  audio while a job is queued or running.

The database and uploaded audio are excluded from Git. Uploads are written with
a generated name and atomic move. The existing maximum upload size and allowed
extension checks remain in force.

Source audio is deleted after completion, failure, cancellation, or explicit
history deletion. Completed transcript text and JSON remain until the user
deletes the history item. There is no automatic result expiration in this
version.

## Components

### Session Middleware

The middleware reads the cookie, validates its shape, hashes it, and resolves an
owner. If it is missing or invalid, it creates a new owner and sets a fresh
cookie on the response. The owner ID is placed on request state for API routes.

### Job Repository

A repository module owns the SQLite schema and all job queries. Its public
methods require an owner ID for user-facing operations. Worker-only claim and
update methods do not expose records through HTTP.

The repository performs conditional state transitions, preventing double
claims and preventing completed or canceled jobs from being overwritten by late
worker updates.

### Background Worker

One process-local worker thread claims the oldest queued job. The existing
transcription service remains responsible for model execution and streaming
partial output. The worker periodically stores the latest progress and checks
`cancel_requested` through a per-job cancellation event.

The worker starts during FastAPI application lifespan and shuts down cleanly.
The existing FIFO queue is replaced as the source of truth by the persistent job
table. Only one job may be running at once.

At startup, jobs left in `running` are moved back to `queued`. They restart from
the beginning because model state cannot be serialized safely. The retained
audio file permits this recovery. If the audio is missing, the job becomes
`failed` with a clear error.

### HTTP API

Owner-scoped endpoints provide:

- create/upload a transcription job;
- list the current browser's jobs newest first;
- read one job and its current progress/result;
- request cancellation;
- delete a terminal history item;
- download completed output as TXT or JSON;
- report aggregate queue counts without exposing owners or filenames.

Download responses use sanitized filenames and `Content-Disposition`.

### Gradio UI

The UI becomes a client of the persistent job API/repository state instead of
owning task execution in `gr.State`. It contains:

- upload and hotwords controls;
- current task status with polling;
- transcript and JSON views restored on page load;
- stop button for queued/running tasks;
- history list with filename, date, and status;
- open, copy, TXT download, JSON download, and delete actions.

The only browser-local state is the protected cookie. A reload reconstructs the
screen from server data. Global queue status may show counts, but never another
user's filename, progress, transcript, or identifiers.

## Data Flow

1. The browser opens the application; middleware resolves or creates its owner.
2. Upload creates a job row and moves audio into the private upload directory.
3. The worker claims the oldest queued job independently of the browser request.
4. Progress and partial text are committed to SQLite during transcription.
5. The UI polls the owner-scoped job endpoint and renders the latest state.
6. On success, the worker stores final text/JSON and deletes the audio.
7. Reloading the page lists the same owner's jobs and reopens the newest active
   or selected item.
8. Downloads are generated from the stored result after owner authorization.

## Error Handling and Recovery

- Invalid upload: reject before creating a runnable job and remove temporary
  data.
- Database write failure during upload: remove the uploaded file and return a
  safe error.
- Transcription failure: store `failed`, retain a sanitized message, and delete
  the audio.
- Browser disconnect: no effect on worker execution.
- Server restart: requeue interrupted `running` jobs and process them again.
- Cancellation: mark the request immediately; queued jobs become `canceled`,
  while running jobs stop at the next supported cancellation checkpoint.
- Missing/corrupt source file: mark the job `failed` and continue with the next
  queued job.
- Cleanup failure: log it without exposing paths; retry best-effort during
  startup cleanup.

Internal exception details and filesystem paths are logged server-side but are
not returned to other users or placed in history.

## Compatibility

The existing synchronous `POST /api/transcribe` contract is retained for
automation clients in this version. It continues to use serialized model access,
but new UI jobs use the persistent job API. Access to old synchronous API
results is not added to browser history unless the API is later given an
authentication scheme.

The worker and synchronous endpoint share one execution lock so they cannot use
the GPU concurrently.

## Testing

Automated tests cover:

- cookie creation, attributes, reuse, and invalid-token replacement;
- token hashing and absence of raw tokens in SQLite;
- strict owner isolation for list, detail, cancel, delete, and download;
- upload validation and path safety;
- persistent FIFO claiming and single active job;
- browser disconnect/reload behavior through API state;
- startup recovery of interrupted jobs;
- progress and successful result persistence;
- failure and cancellation transitions;
- audio cleanup for every terminal state;
- TXT/JSON content and safe download filenames;
- UI creation and history refresh behavior;
- compatibility and mutual exclusion of the synchronous API.

The existing unit tests remain green. New repository tests use temporary SQLite
databases and directories; worker tests use a mocked transcription service and
do not require a GPU model.
